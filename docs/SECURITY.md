# Security model

- **Local only.** Scanning, selection and building happen on this computer. Inventories are never uploaded.
- **Read-only discovery.** Adapters run listing commands (`rpm -qa`, `flatpak list`, `snap list`, `Get-AppxPackage`, `brew info`, `port installed`) and read metadata files (registry uninstall keys, Info.plist, nuspec, Scoop manifests, receipts, AppStream metainfo). Git repositories are parsed from files; `git` is never executed. Homebrew runs with auto-update and analytics turned off; winget is not run because it may contact Microsoft. Folders outside standard app locations are scanned only after the user approves them.
- **Nothing implicit.** An empty selection is an error. Every app part and folder is an explicit choice.
- **Secrets withheld by default.** SSH/GnuPG keys, keyrings and macOS Keychains, Windows saved credentials and data-protection keys, password databases, browser logins/cookies, cloud/registry tokens, private keys and recovery codes are excluded by path rules. Including one requires an explicit per-path opt-in with a warning; encrypting the snapshot then protects it.
- **Sources are never modified.** Builds only read sources and write into a hidden staging folder, then rename. An existing snapshot is never overwritten.
- **Untrusted snapshots.** Manifests are validated strictly (see MANIFEST.md); every restored file is re-hashed and discarded on mismatch; restores use `create_new` (never overwrite), refuse to write through symlinks, and only recreate relative in-root symlinks.
- **Elevation only when needed and approved.** Files are restored only inside the user's home. Flatpak apps install per user and program files are copied as the user. Only system package installs (DNF/RPM, APT, Zypper, Pacman, snap) need administrator rights: the restore plan marks them "needs administrator password", the confirmation names them, and then `sudo` (CLI, asked once up front) or `pkexec` (desktop app) asks for the password for one package-manager command per manager. Source builds and Flatpak, Homebrew and program installs run as the user. The GUI and engine never run as root themselves.
- **Installers are untrusted input too.** Each installer file's SHA-256 is checked right before use, and a mismatch installs nothing. Recipes are typed; names are validated before they reach a command line. RPMs already on the target are never up- or downgraded. An app counts as installed only when the package manager lists it afterwards (`flatpak info`, `rpm -q`, `snap list`) or the copied program matches its checksum and is executable.
- **Offline first; downloads only for what the snapshot lacks.** Installers are collected while building: RPMs and snaps are downloaded from their configured repositories/store (RPM signatures are checked with `rpmkeys` and recorded), Flatpak bundles are made from the local repository, and restore installs them with `--cacheonly`/`--disablerepo=*`, `--no-related` and local files only. Only an app the snapshot holds no usable installer for is installed online, and only when the restore may use the internet (`--offline` and the Settings switch turn it off). It is then installed with the new computer's own package manager (winget, Homebrew, Flatpak from Flathub per user, APT/DNF/Zypper/Pacman, snap) or a verified download, chosen by exact IDs only: the app's own package name, the vetted registry's IDs or the app's own GitHub repository. Nothing is matched by name, so an unrelated app is never substituted. Package names are checked (`plain_name`) before they reach a fixed command line; the APT install runs one fixed script whose package names arrive as arguments. An app counts as installed only when the package manager lists it afterwards (`flatpak info`, `dpkg-query`, `rpm -q`, `pacman -Q`, `snap list`, `brew list`, `winget list`) or the installer-type check below confirms it.
- **One password prompt per package manager.** System packages for all chosen apps are installed in one elevated command per package manager (unknown names are filtered out first, so one cannot stop the others); the CLI asks `sudo` once before anything starts. Nothing else runs elevated.
- **Source builds are visible and pinned.** A GitHub checkout that uses Cargo, Go or pipx can be rebuilt on the new computer when no package or release exists. It is a separate, labelled item in the restore preview (it runs the project's own build code; untick it to skip, or turn source builds off in Settings or with `--no-source-builds`), and builds the exact recorded commit (`cargo install --git … --rev`, `--locked` when the project has a lock file; `go install …@<commit>`; `pipx install git+…@<commit>`). A missing build tool is installed first from the system's package manager. Builds install into the user's own folders (`~/.local`), never system-wide.
- **GitHub requests.** Without a token GitHub allows 60 API requests an hour; a rate-limit refusal says when it resets (a 403 with requests left is reported as an access problem). The desktop app keeps a personal access token in the system keyring (Settings → GitHub) and hands it to the engine in memory; the CLI uses `GITHUB_TOKEN`/`GH_TOKEN`, or else the signed-in GitHub CLI's token (`gh auth token`, asked once). The token is passed to curl in a temporary file created new and readable only by the user, never on the command line, and only to `api.github.com` (files of private repositories are fetched through the API with it). It never appears in manifests, scripts, reports or the diagnostic log. GitHub answers are cached on disk with their ETags.
- **Downloads are pinned and verified.** For Windows, macOS and other-architecture targets the build (and, for apps the snapshot lacks, the restore) looks the app up in a vetted catalog (winget's community manifests on GitHub, Homebrew's cask API, the app's GitHub releases, or a link plus SHA-256 the user registered) and downloads with the system `curl`: HTTPS only, redirects kept on HTTPS, `~/.curlrc` ignored. The file must match the SHA-256 the catalog publishes, or it is deleted. Two sources sometimes publish no checksum: Homebrew casks marked `no_check` (vendor links that always serve the newest version, such as Spotify's) and GitHub assets with neither a digest nor an entry in the release's checksum list. Those are taken only over HTTPS from the catalog's or the app's own repository's link; the file's SHA-256 is computed while building and pinned in the snapshot (and checked again before installing), and the build report, the evidence and `RESTORE.md` say that no checksum was published. A restore that would download such a file itself needs approval (the setting "Also allow downloads that publish no checksum", or `--allow-unverified`). Winget entries and links the user registers always need a checksum. The release tag the old computer had is tried first, then the newest release (stable before prerelease, never a draft) with a file for the target. Archives (`.tar.gz`, `.zip`) are checked before unpacking (no absolute paths, `..` or links; zip central directories are read first) and the unpacked tree is checked for links leading out of it; a single program is kept, or a program that ships its own libraries goes into its own folder (`~/.local/opt/<App>`, Windows Programs), linked into `~/.local/bin`, never over a folder Simple Setup did not make. Windows `.exe` installers are run unattended only with the silent switches winget's manifest lists for them, or when recognised as NSIS, Inno Setup or WiX by marks in the file. Linux programs must be built for the target's processor (checked in the ELF header). Downloads are kept per snapshot in the user's cache folder and checked again before use, so a restore resumes after an interruption without downloading again. Only what is needed for the selected apps and targets is requested, and nothing about the computer is sent beyond those requests. Architecture-mismatched installers (e.g. x64 for ARM64 Windows) are never chosen, since they would rely on emulation.
- **Windows and macOS installs.** Installers with known unattended options are started with switches fixed in code (MSI, NSIS, Inno Setup, WiX bundles). Other `.exe` installers run only with the silent switches from the winget manifest (`InstallerSwitches.Silent`, or none when the manifest's only install mode is silent). Those switches are stored in the recipe, accepted only as up to 8 plain words of letters, digits and `/_.:=,+-` (no quotes, spaces, placeholders or shell characters, checked again when a snapshot is read), and passed as arguments to the checksum-verified installer, never through a shell. MSIX packages are installed per user with `Add-AppxPackage` (the path in an environment variable, never in PowerShell code). macOS installer packages are installed with `installer` only after `pkgutil --check-signature` accepts them, with administrator approval. Other installers (`.exe` without such switches, zips without a single app) stay in the snapshot for the user to open, and the item is reported as manual. A disk image that does not name its app (GitHub releases) is opened read-only on the Mac and installed only if it holds exactly one app. When Windows reports that an installer needs administrator rights, it is started through PowerShell `Start-Process -Verb RunAs`, so Windows shows its own consent prompt; the file path and arguments are passed in environment variables, never inside PowerShell code. macOS apps are copied into `/Applications` (or `~/Applications` if that is not writable) without a password. An app counts as installed only when it then appears in the installed-programs list or as an app bundle with the expected bundle identifier.
- **Settings converters choose their own destinations.** Settings restored on another operating system are placed by per-app adapters whose target folders are fixed in code; a snapshot cannot direct files elsewhere. Files the adapter does not know to be portable stay in the snapshot.
- **Distribution profiles are data.** Which package manager, package names and repositories a Linux computer uses comes from its profile (see PLATFORMS.md). Imported profiles are size-limited, read with strict schemas (JSON, or YAML with a parser that limits aliases and nesting) and validated; they cannot carry commands, except a user profile's custom package-manager commands: fixed argument lists (never a shell; no shells, interpreters or elevation tools as the program; placeholders only as whole arguments) that run only after the user trusts that exact command set (the trust is a SHA-256 of the commands; any change drops it) and that the restore plan lists as needing approval. The only commands shipped with Simple Setup are the Gentoo (Portage) and NixOS (`nix-env`) profiles'; they are part of the program and need no approval per app, an official update may only repeat them unchanged, and a user's copy of them under another ID still needs the user's trust. Official profile updates come from this project's GitHub release, checked like app updates, and must be newer than the ones in use. The same rules apply to the user's own app-registry entries (`apps.json`): validated as a whole, names checked like package names, settings folders only under `~/`. Packages that a distribution's package manager offers only from a repository its profile does not list as its own (a PPA, COPR, a vendor repository) are tried last and need approval.
- **IPC allow-list.** The webview can call only the commands listed in `src-tauri/build.rs`; it has no shell, file-system or HTTP plugins. CSP forbids remote content.
- **Encrypted snapshots (optional).** A random X25519 key encrypts every copied file and the full manifest (standard `age` format). The key is stored in the snapshot only encrypted with the user's password (age scrypt) and is shown once after the build as a recovery key; it is never written to the snapshot, reports or logs in plain form. Without the password, a snapshot shows only its name, date, source computer, target platforms and readiness; stored file names are keyed hashes (`data/xx/…`), and reports are encrypted too. Installer files are public downloads and are not encrypted, so their names show which apps are included. Integrity can be verified without the password. Losing both the password and the recovery key means nobody can open the snapshot. Passwords must have at least 8 characters; they are typed without echo or read from a file, and the desktop app keeps them only in memory.
- **Network transfer.** A computer listens only while its Receive screen (or `simple-setup receive`) is open, on a random port, and announces itself over mDNS (`_simple-setup._tcp`) only then. It shows an 8-digit pairing code; the sender types it and both sides run SPAKE2 with it, so the code never crosses the network and an eavesdropper cannot test guesses offline. Each connection allows one online guess, and the receiver stops listening after 5 wrong codes. After pairing, every message is encrypted and authenticated with ChaCha20-Poly1305 using separate keys per direction (HKDF-SHA256 from the SPAKE2 key, counter nonces), so tampering or replay breaks the connection. The receiver sees the sending computer and the snapshot's name, size, encryption and target platforms, and must accept before anything is written. Offered paths are validated like manifest paths; each file is checked against its SHA-256 as it arrives (damaged files are discarded) and the snapshot's own checksum list must match the offer before the folder is renamed into place. Interrupted transfers resume from what was already received and checked. A sender that knows the code can, instead of offering a snapshot, ask what the receiving computer is (the Transfer flow does this before building): the receiver answers with its system, distribution profile, package managers, portable formats and whether it is online, nothing about its files or apps, and keeps waiting; the person there sees that it was asked. The sender uses that answer only to plan, drops any custom commands in it, and never runs anything from it. Receiving never restores anything by itself unless the person at the receiving computer chose "Restore automatically when it arrives" (or `receive --restore`) before pairing; even then only the verified snapshot is restored, an encrypted one waits for its password, and administrator prompts still appear.
- **Self-update.** The app checks `github.com/fleetwoodjohnr/simple-setup` for the latest published release (drafts and prereleases are never offered) at most once a day when the setting is on, never in development builds, and on request. The file for this installation type and processor is downloaded over HTTPS into the user's cache folder (resumable) and used only if it matches GitHub's SHA-256 digest and the release's `SHA256SUMS` (both must agree when both exist) and looks like the expected file type. Installing goes through the platform's installer (apt/dnf with one password prompt, `msiexec`, the NSIS installer which asks Windows for consent); AppImages and app bundles are swapped in place, keeping the old copy until the new one has started. Settings and snapshots are never touched. Releases are not code-signed for Linux; integrity rests on HTTPS to GitHub plus the published checksums.
- **Per-app install commands.** A snapshot (format 4) may carry the user's own install command for an app. It is shown exactly as it will run, with no control characters allowed, so nothing is hidden. It always needs its own approval: choosing the item does not approve it, and `--yes` does not either; `--approve-custom ITEM` does. It never runs through a shell that Simple Setup adds. Developer tools (`cargo install`, `pipx`, `npm -g`) run the package's own build or install code and need approval for the same reason. Every new field of format 4 is validated as untrusted input; a hostile value makes the snapshot unreadable instead of reaching a command, a path or the screen.
- **Install scripts.** `export-script` writes the restore's own fixed command lines into a POSIX shell or PowerShell script. Every argument is quoted (in PowerShell, all four single-quote characters are doubled), and names and reasons in comments are flattened to one line. Ways that need an approval, source builds and the user's own commands appear only as comments to review. Downloads are pinned to the SHA-256 their source publishes and are fetched into a private folder made for that run (`mktemp -d`, mode 0700); a shared folder in `/tmp` would let another local user swap a checked file before it was installed. No token is ever written.
- **Packed snapshots.** A `.tar.gz` made by `snapshot pack` is untrusted when opened. It is read once to check every entry (plain files and folders in one top folder; no absolute paths, `..`, links or devices) and the free space, then extracted into a hidden folder that becomes the snapshot only after every file matches its checksum.
- **Restoring over existing files.** Replace moves the existing file to `~/.simple-setup-backup/<time>/` before writing; Skip and Keep both leave it untouched. The old home folder (recorded in format 4, and only in the encrypted part of an encrypted snapshot) is replaced by the new one only in small UTF-8 text settings of apps marked `home_paths` and in shell settings, after the file matched its checksum, and only where the whole folder name matches.
- **Transfers reconnect, never re-pair silently.** After a dropped connection the sender connects again with the same code and must reach the same computer; the receiver does not ask again for a snapshot it already accepted. Files the receiving computer already has (in other snapshots in the same folder, or as another copy in the same offer) are linked or copied and checked against the offered SHA-256 before the sender is told they are there. A different snapshot with the same name is kept, and the new one is saved beside it. Receiving can use a fixed port for a VPN or port forwarding; a forwarded port is open to the internet while receiving, so it should be closed afterwards (the pairing code still protects the transfer).
- **Diagnostic log.** Commands (program and arguments, with credential-looking arguments hidden), exit codes, durations, download addresses and checksums, and transfer events are written to a size-limited log in the user's state folder. Tokens, passwords and file contents are never written. It leaves the computer only when the user exports it.
