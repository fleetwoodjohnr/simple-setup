# Security model

- **Local only.** Scanning, selection and building happen on this computer. Inventories are never uploaded.
- **Read-only discovery.** Adapters run listing commands (`rpm -qa`, `flatpak list`, `snap list`, `Get-AppxPackage`, `brew info`, `port installed`) and read metadata files (registry uninstall keys, Info.plist, nuspec, Scoop manifests, receipts, AppStream metainfo). Git repositories are parsed from files; `git` is never executed. Homebrew runs with auto-update and analytics turned off; winget is not run because it may contact Microsoft. Folders outside standard app locations are scanned only after the user approves them.
- **Nothing implicit.** An empty selection is an error. Every app part and folder is an explicit choice.
- **Secrets withheld by default.** SSH/GnuPG keys, keyrings and macOS Keychains, Windows saved credentials and data-protection keys, password databases, browser logins/cookies, cloud/registry tokens, private keys and recovery codes are excluded by path rules. Including one requires an explicit per-path opt-in with a warning; encrypting the snapshot then protects it.
- **Sources are never modified.** Builds only read sources and write into a hidden staging folder, then rename. An existing snapshot is never overwritten.
- **Untrusted snapshots.** Manifests are validated strictly (see MANIFEST.md); every restored file is re-hashed and discarded on mismatch; restores use `create_new` (never overwrite), refuse to write through symlinks, and only recreate relative in-root symlinks.
- **Elevation only when needed and approved.** Files are restored only inside the user's home. Flatpak apps install per user and program files are copied as the user. Only system package installs (DNF/RPM, APT, Zypper, Pacman, snap) need administrator rights: the restore plan marks them "needs administrator password", the confirmation names them, and then `sudo` (CLI, asked once up front) or `pkexec` (desktop app) asks for the password for one package-manager command per manager. Source builds and Flatpak, Homebrew and program installs run as the user. The GUI and engine never run as root themselves.
- **Installers are untrusted input too.** Each installer file's SHA-256 is checked right before use, and a mismatch installs nothing. Recipes are typed; names are validated before they reach a command line. RPMs already on the target are never up- or downgraded. An app counts as installed only when the package manager lists it afterwards (`flatpak info`, `rpm -q`, `snap list`) or the copied program matches its checksum and is executable.
- **Offline first; downloads only for what the snapshot lacks.** Installers are collected while building: RPMs and snaps are downloaded from their configured repositories/store (RPM signatures are checked with `rpmkeys` and recorded), Flatpak bundles are made from the local repository, and restore installs them with `--cacheonly`/`--disablerepo=*`, `--no-related` and local files only. Only an app the snapshot holds no usable installer for is installed online, and only when the restore may use the internet (`--offline` and the Settings switch turn it off). It is then installed with the new computer's own package manager (winget, Homebrew, Flatpak from Flathub per user, APT/DNF/Zypper/Pacman, snap) or a verified download, chosen by exact IDs only: the app's own package name, the vetted registry's IDs or the app's own GitHub repository. Nothing is matched by name, so an unrelated app is never substituted. Package names are checked (`plain_name`) before they reach a fixed command line; the APT install runs one fixed script whose package names arrive as arguments. An app counts as installed only when the package manager lists it afterwards (`flatpak info`, `dpkg-query`, `rpm -q`, `pacman -Q`, `snap list`, `brew list`, `winget list`) or the installer-type check below confirms it.
- **One password prompt per package manager.** System packages for all chosen apps are installed in one elevated command per package manager (unknown names are filtered out first, so one cannot stop the others); the CLI asks `sudo` once before anything starts. Nothing else runs elevated.
- **Source builds are visible and pinned.** A GitHub checkout that uses Cargo, Go or pipx can be rebuilt on the new computer when no package or release exists. It is a separate, labelled item in the restore preview (it runs the project's own build code; untick it to skip, or turn source builds off in Settings or with `--no-source-builds`), and builds the exact recorded commit (`cargo install --git … --rev`, `--locked` when the project has a lock file; `go install …@<commit>`; `pipx install git+…@<commit>`). A missing build tool is installed first from the system's package manager. Builds install into the user's own folders (`~/.local`), never system-wide.
- **GitHub requests.** Without a token GitHub allows 60 API requests an hour; a rate-limit refusal says when it resets. A token in `GITHUB_TOKEN`/`GH_TOKEN` is passed to curl in a temporary file readable only by the user, never on the command line, and only to `api.github.com`.
- **Downloads are pinned and verified.** For Windows, macOS and other-architecture targets the build (and, for apps the snapshot lacks, the restore) looks the app up in a vetted catalog (winget's community manifests on GitHub, Homebrew's cask API, the app's GitHub releases, or a link plus SHA-256 the user registered) and downloads with the system `curl`: HTTPS only, redirects kept on HTTPS, `~/.curlrc` ignored. The file must match the SHA-256 the catalog publishes, or it is deleted; downloads without a published checksum (Homebrew `no_check`, GitHub assets with neither a digest nor an entry in the release's checksum list) are refused and reported. The release tag the old computer had is tried first. Archives (`.tar.gz`, `.zip`) are unpacked with the system's `tar`/`unzip` and only a single program inside is kept (regular files only; links are ignored). Windows `.exe` installers are run unattended only when recognised as NSIS, Inno Setup or WiX by marks in the file. Downloads are kept per snapshot in the user's cache folder and checked again before use, so a restore resumes after an interruption without downloading again. Only what is needed for the selected apps and targets is requested, and nothing about the computer is sent beyond those requests. Architecture-mismatched installers (e.g. x64 for ARM64 Windows) are never chosen, since they would rely on emulation.
- **Windows and macOS installs.** Only installer types with known unattended options are started (MSI, NSIS, Inno Setup, WiX bundles), with switches fixed in code; catalog-supplied switches are ignored. Other installers (`.exe` of unknown type, `.msix`, `.pkg`, disk images without a known app) stay in the snapshot for the user to open, and the item is reported as manual. When Windows reports that an installer needs administrator rights, it is started through PowerShell `Start-Process -Verb RunAs`, so Windows shows its own consent prompt; the file path and arguments are passed in environment variables, never inside PowerShell code. macOS apps are copied into `/Applications` (or `~/Applications` if that is not writable) without a password. An app counts as installed only when it then appears in the installed-programs list or as an app bundle with the expected bundle identifier.
- **Settings converters choose their own destinations.** Settings restored on another operating system are placed by per-app adapters whose target folders are fixed in code; a snapshot cannot direct files elsewhere. Files the adapter does not know to be portable stay in the snapshot.
- **IPC allow-list.** The webview can call only the commands listed in `src-tauri/build.rs`; it has no shell, file-system or HTTP plugins. CSP forbids remote content.
- **Encrypted snapshots (optional).** A random X25519 key encrypts every copied file and the full manifest (standard `age` format). The key is stored in the snapshot only encrypted with the user's password (age scrypt) and is shown once after the build as a recovery key; it is never written to the snapshot, reports or logs in plain form. Without the password, a snapshot shows only its name, date, source computer, target platforms and readiness; stored file names are keyed hashes (`data/xx/…`), and reports are encrypted too. Installer files are public downloads and are not encrypted, so their names show which apps are included. Integrity can be verified without the password. Losing both the password and the recovery key means nobody can open the snapshot. Passwords must have at least 8 characters; they are typed without echo or read from a file, and the desktop app keeps them only in memory.
- **Network transfer.** A computer listens only while its Receive screen (or `simple-setup receive`) is open, on a random port, and announces itself over mDNS (`_simple-setup._tcp`) only then. It shows an 8-digit pairing code; the sender types it and both sides run SPAKE2 with it, so the code never crosses the network and an eavesdropper cannot test guesses offline. Each connection allows one online guess, and the receiver stops listening after 5 wrong codes. After pairing, every message is encrypted and authenticated with ChaCha20-Poly1305 using separate keys per direction (HKDF-SHA256 from the SPAKE2 key, counter nonces), so tampering or replay breaks the connection. The receiver sees the sending computer and the snapshot's name, size, encryption and target platforms, and must accept before anything is written. Offered paths are validated like manifest paths; each file is checked against its SHA-256 as it arrives (damaged files are discarded) and the snapshot's own checksum list must match the offer before the folder is renamed into place. Interrupted transfers resume from what was already received and checked. The sender learns only the receiver's name and platform. Receiving never restores anything by itself unless the person at the receiving computer chose "Restore automatically when it arrives" (or `receive --restore`) before pairing; even then only the verified snapshot is restored, an encrypted one waits for its password, and administrator prompts still appear.
- **Self-update.** The app checks `github.com/fleetwoodjohnr/simple-setup` for the latest published release (drafts and prereleases are never offered) at most once a day when the setting is on, never in development builds, and on request. The file for this installation type and processor is downloaded over HTTPS into the user's cache folder (resumable) and used only if it matches GitHub's SHA-256 digest and the release's `SHA256SUMS` (both must agree when both exist) and looks like the expected file type. Installing goes through the platform's installer (apt/dnf with one password prompt, `msiexec`, the NSIS installer which asks Windows for consent); AppImages and app bundles are swapped in place, keeping the old copy until the new one has started. Settings and snapshots are never touched. Releases are not code-signed for Linux; integrity rests on HTTPS to GitHub plus the published checksums.
